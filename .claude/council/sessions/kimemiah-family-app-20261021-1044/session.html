Architect Position — Kimemiah family app: architecture, schema, identity, offline sync, push

Core recommendation: One Next.js PWA on Vercel talking straight to Supabase (Postgres + RLS + one Edge Function + pg_cron). Phones write locally first into IndexedDB with an outbox, and every table is shaped so sync is boring: client-generated UUIDs, soft deletes, server updated_at cursors, and append-only rows (stock movements, money entries) wherever two phones might collide.

Key argument: The data is tiny (6 people, ~60 stock items, a few hundred rows a month), so the hard parts are identity and conflicts, not scale. Identity: the shared PIN gates the device, a profile picker names the person. Each phone calls Supabase anonymous sign-in, so it gets its own auth user. It then posts the PIN to one Next.js route (/api/unlock). That route checks a bcrypt hash held in a server env var, rate-limits by device and IP (5 tries, then a 15-minute lockout), and uses the service role to set app_metadata.household = true on that device. RLS on every table is one rule: is_household() reads that claim. After unlock, "Who are you?" stores member_id on the device row and locally. Every write carries actor_id, so thank-yous, claims and spending all record a name. This attribution runs on trust inside a family, not on security, and that's fine. Any phone can be revoked by setting devices.revoked_at, which clears the claim, without changing the PIN for everyone. Offline: Dexie (IndexedDB) mirrors each table. User actions apply locally and append to an outbox. A sync loop runs on reconnect, on focus, and every 30 s while online. It pushes the outbox through one RPC, apply_mutations(jsonb[]), which is idempotent on mutation id. It then pulls each table where updated_at > cursor, and Realtime nudges the pull while the app is open. Conflict policy, per data type: (1) Stock is never set as an absolute value. Each +/− is a stock_movements row with a delta, and a trigger keeps stock_items.have_qty as the running sum, so two offline phones simply add up. (2) Money entries are insert-only, so they never conflict; a correction is a new reversing entry. (3) Claiming a job or a cook slot goes through a server-checked RPC where the first claim wins. A late offline claim comes back rejected and the UI says "Sister already took this." (4) Everything else (titles, notes, contacts, meal slots, budgets) is last-write-wins per row by server receipt order. Push: Web Push with VAPID keys. Phones store subscriptions in push_subscriptions. An activity insert trigger calls the notify Edge Function through pg_net, and the function sends with web-push, skipping the actor's own devices. pg_cron runs daily for three jobs: the 3-day "Needs a volunteer" flag, regenerating repeating jobs, and low-stock or meeting-tomorrow reminders. The same activity table drives the Home feed, so one event log serves both. Repo: a single app, no monorepo tooling:

Risks if ignored:

  • Structural: If Have is stored as an absolute value, offline edits overwrite each other and stock silently drifts. Without deleted_at, the delta pull can't propagate deletes, and removed rows come back as ghosts on other phones.
  • Security/performance: A 4–6 digit PIN on a public URL can be brute-forced unless the check stays server-side with rate limiting and per-device revocation. Never put the PIN in client JS, and never ship the service-role key to the browser.
  • Integration/platform: iPhone web push only works after "Add to Home Screen" on iOS 16.4 or later, so install is a hard step in onboarding. Supabase free projects pause after 7 days without activity; daily family use and the daily cron should cover this, but watch it during holidays.

Dependencies on other domains:

  • Skeptic/Guardian: confirm the PIN length, the lockout numbers and the revocation flow, and decide whether money edits are allowed or must use reversing entries.
  • Pathfinder: Serwist caching strategy, the iOS install prompt, and permission UX for push.
  • Advocate: the "Who are you?" picker (avatars, switching person on a shared phone), how sync and rejected-claim states appear, and which events notify by default.
  • Artisan/Tuner: the GSAP + Lenis + React Bits budget on low-end Android. Sync must never wait on an animation.
  • Strategist: build order. Sync and identity come first, since all 8 sections reuse them.
  • Craftsman: two-device offline conflict tests for stock deltas and job claims.

Advocate Position — Kimemiah family app UX

Core recommendation: Build every screen around a five-second job done on a cheap Android phone, often offline, with no question of "who am I" and no chance of public shame. Ship all 8 sections, but only three need to feel great on day one: the stock tap, the market run, and picking up a job. The rest can be plain and still correct.

Key argument: Mom opens the app while cooking and sees the unga is nearly finished. She taps −, the item turns amber, and an "Undo" bar appears for 5 seconds. No confirmation dialog, no spinner, no sign-in prompt, and it works with no data bundle. If that tap ever takes longer than the 5 seconds it would take to shout "unga imeisha!" across the house, people stop using the app, and a stock list that is wrong is worse than no list. The same goes for everything else: attribution has to be automatic (the shared PIN plus a "Who's using this phone?" name picker, asked once per device and remembered, switchable from the avatar), and actions save on the phone first and sync afterwards, with a small "Saved on this phone · will sync" chip instead of error popups. The sensitive part is the social layer. In this house, money comes from Dad and three of five adults don't earn. The app must never turn into a scoreboard. That means no per-person totals anywhere: no "jobs done by Sam: 12", no "spent by person" chart. The "Needs a volunteer" flag describes the job ("waiting 3 days"), never the people. Dropping a job is neutral ("Back on the board"). A thank-you is one tap (an Asante button with an optional short note) that only the recipient gets as a notification. Money-in entries can be thanked too, so Dad sees gratitude, not just a ledger. Spending entries stay strictly factual, as 01 already says.

Revisions to earlier plan decisions:

  • Navigation: the bottom bar stays at 5 (Home, Stock, Jobs, Meals, Money). Budget becomes a tab inside Money (it is about the same money), so More holds only Meeting and Contacts. Contacts also become searchable from Home, because a fundi number is needed in a hurry.
  • Home becomes "Today": at most 5 cards, ordered by urgency (Out items, someone heading to the shop, open help requests, today's cook, money left). Thank-yous go on the Jobs tab, not Home, so nobody's absence from them is on display every morning.
  • Stock entry: keep + / −, but add a tap on the status chip to set OK / Low / Out in one go for produce (nobody counts sukuma bunches). Exact counts stay for packaged goods.
  • Language: English UI using the family's own words for items and roles (unga, sukuma wiki, mama mboga, fundi, KPLC tokens), plus "Asante" on the thank-you button. No Swahili toggle in v1. Money is shown as KES 1,250 (no decimals, comma thousands), dates as Tue 21 Oct, everything in Africa/Nairobi time.
  • Motion: GSAP for the tick, the undo bar and a small thank-you burst only. Turned off under reduced-motion and kept off the stock list for budget phones. React Bits is fine for the thank-you moment, not for core lists.

Notifications: send / never send

  • Send: "Brian is going to the market in ~20 min, add requests" (the most valuable one). Gas or tokens hit Out. A help request is posted. Someone thanked you. Money received (to everyone, neutral wording). Meeting day at 9am. The monthly summary to Dad.
  • Never: unpicked-job nags, a push for every Low item, "you haven't opened the app", personal reminders sent by other people, spending alerts, anything comparing people. Quiet hours 21:00 to 07:00, and each person can mute each type in settings.

Onboarding at the meeting: load the starter stock, jobs and meals before the meeting so nobody's first screen is empty. Do a private walkthrough with Mom first. At the meeting, the steps go open link → Add to Home Screen (iPhone push only works after this) → PIN → pick your name → allow notifications, asked after saying which ones they'll get. Their first tap comes during the existing appreciation round, where each person sends one Asante in the app, so the first experience is warmth rather than a chore. Dad gets the link on WhatsApp with three screenshots and a "Money" deep link.

Risks if ignored:

  • Attribution friction or slow taps make people stop updating within two weeks, and the stock list drifts away from reality.
  • Per-person counts, or nags about unpicked jobs, turn "volunteer, don't assign" into public guilt for the members who don't earn, and they quietly stop opening it.
  • If Add to Home Screen is skipped at the meeting, iPhone users never get push and the market-run coordination fails.

Dependencies:

  • Architect: a local-first store with optimistic writes. A device-level "current member" setting under the shared PIN. Conflict rule for stock is "last tap wins plus a visible history" (counts change by deltas, not overwrites).
  • Pathfinder: PWA install flow, web push on Android and on iOS 16.4+, quiet hours, deep links.
  • Skeptic/Guardian: the PIN design must not add a sign-in step to every visit (long-lived device session).
  • Artisan/Tuner: 48px touch targets, WCAG AA contrast in both themes, colour plus label for status (never colour alone), motion budget for low-end phones.

Skeptic Position: Kimemiah family app (shared PIN, money records, offline, push, all 8 sections)

Core recommendation: Keep the shared PIN, but treat it as a gate and not an identity. Check it on the server, rate-limit it, and add a "Who's using this phone?" picker so every action is attributed. Make money and stock records append-only, and take nightly off-Supabase backups. The bigger risk is scope: offline sync and push for all 8 sections in release 1 is where this project actually fails.

Key argument: Six months from now, the likely failure is not a hacker. One of three things happens. (1) A dispute: "who logged KES 3,000 at Naivas?", and nobody can answer, because everyone signed in as "the family" and someone edited or deleted the row. (2) Data loss: two phones changed stock offline and last-write-wins dropped one change, or iOS Safari cleared a non-installed site's IndexedDB queue after 7 days without use, or the free Supabase project paused or broke and nobody had a backup (the free tier has no downloadable backups). (3) The app never shipped, because offline sync, push and auth were built across 8 sections at once. A shared PIN on a public URL is a real but modest risk if it is checked server-side and throttled. Nothing here can move money. The worst disclosure is family names, contacts and household spending. That deserves care, not bank-grade security.

Minimal PIN hardening (keeps the user's choice):

  • PIN of at least 6 digits, stored only as an argon2/bcrypt hash on the server. Never compare it in client code.
  • Check it in a Next.js route handler. Rate limit: 5 failures per IP per 15 minutes, plus a global cap (say 30 failures an hour) that locks sign-in for an hour and sends a push to the user.
  • After a correct PIN, the person picks their name. Server-side, the route signs in as that member's own Supabase Auth user (6 users with random passwords the server holds), so you get real per-member sessions, refresh tokens and auth.uid() for RLS. Long-lived device session, about 90 days.
  • RLS on every table: authenticated only, with no anon policies at all, so the public anon key exposes nothing. Keep the service-role key server-only (never NEXT_PUBLIC_). Put the PIN hash, service key and VAPID private key in a git-ignored .env, with a setup script and .env.example as CLAUDE.md requires.
  • "Change PIN" plus "Sign out all devices" (Supabase admin global sign-out for all 6 users). Use it when the PIN leaks, which with 6 people it will.
  • Set noindex, and keep Vercel Deployment Protection on preview URLs (previews use the same database).

Push back on overbuild:

  • Offline for everything is overbuilt. Make offline writes work only where signal fails: stock +/-, shopping ticks and "Put away", and queued money entries. Everything else is a read-only cache. Store stock changes as deltas (stock_movements: +2 / -1, client UUID, idempotent insert) instead of overwriting have. That removes most conflict handling. Show an "N changes not synced" badge.
  • Push: keep it to 3 events at most ("I'm going to [shop]", a job needs a volunteer, a meeting reminder). iOS only delivers push to a PWA added to the home screen (16.4+), and permission must come from a tap. Subscriptions expire, so delete them on a 404/410. Vercel Hobby cron runs once a day, which suits the 3-day volunteer flag. Never put money amounts in a push payload, because lock screens show them.
  • "All 8 at once": fine as a goal for the meeting, but build the core first (stock/shopping, jobs, money, auth, backups). Meals, contacts, meeting and budget are mostly simple CRUD on top. Push and offline go in a hardening pass after that, not alongside it. Lenis smooth scroll and heavy React Bits effects on budget Android phones work against a daily-use tool. Motion should stay light.

Risks if ignored:

  • High (integrity/family trust): with editable, unattributed money rows, nobody can settle a spending dispute, and the summary sent to Dad stops being trustworthy.
  • High (data loss): last-write-wins sync plus no backups means silent loss of stock and money history, and it can't be recovered.
  • High (scope): offline, push and PIN-auth across 8 sections means the meeting date slips, or it ships fragile and the family drops it after week one.

Dependencies on other domains:

  • Architect: an append-only money_entries table with voids_entry_id corrections, created_by and device_id; a stock_movements delta log; an audit_log written by a trigger.
  • Operator: a nightly GitHub Action that runs pg_dump into encrypted storage (it doubles as a keep-alive ping), the setup script, and a restore drill once.
  • Pathfinder: the iOS install-to-home-screen prompt, the storage-eviction caveat, and which push events to send.
  • Craftsman: sync tests (two offline devices, the same item, replay twice, and the expected final count).
  • Advocate: an easy name picker and "switch person" so attribution doesn't add friction.

Pathfinder Position — Kimemiah family app (PWA, offline, push)

Core recommendation: Keep it a PWA. No native wrapper for v1. Build one precached app shell in Chrome, keep all data in IndexedDB (Dexie) with an outbox that syncs when the app is open, and use VAPID web push. Treat Background Sync as a bonus on Android and assume it doesn't exist on iPhone.

Key argument: Start from the phone in the hand: a 2-3 GB RAM Tecno/Infinix/Samsung A-series on Android 12-14, Chrome, a daily data bundle, and maybe one iPhone. A PWA covers every v1 need on that device: install to home screen, offline use, push, tel: links, and the share sheet. A Capacitor or TWA wrapper adds a Play Store account, signing keys, review cycles and an APK download, and it still can't reach the iPhone without a Mac and $99 a year. What it would add is more reliable push, and v1 can live without that. Revisit only if push turns out unreliable in practice.

Shape of the app:

  • Shell, not server pages. Next.js App Router, but every section renders on the client from Dexie under one precached shell. Server Components that fetch data break offline navigation. Use Serwist (successor to next-pwa): precache the build, cache-first for hashed static assets, an offline fallback for navigations, and no service-worker caching of Supabase API calls. Data goes through Dexie, never the HTTP cache.
  • Data flow. Reads come from Dexie. Writes go to Dexie and an outbox table at once (optimistic), then push to Supabase. Flush the outbox on app open, on online, on visibilitychange, and every 30 s while the app is in the foreground. Register a Background Sync tag as well; on Android Chrome it flushes after the app closes, and iOS ignores it. Supabase Realtime runs only while the app is in the foreground. Stock +/− must sync as deltas (-1 beans), not absolute values, so two phones editing offline merge cleanly.
  • Storage survival. Call navigator.storage.persist() after install. In a Safari tab, iOS deletes site storage after 7 days without use; home-screen apps are exempt, which is one more reason to push installs. Supabase stays the source of truth, so an evicted phone re-downloads everything. Only unsynced outbox rows are at risk, so show a "3 changes waiting to sync" badge.
  • Push. Use the web-push library from a Vercel route (or a Supabase Edge Function) with VAPID keys created by the setup script into .env. Android Chrome receives push even without install. iPhone needs iOS 16.4+, home-screen install, and a permission request triggered by a tap. Ask after the first meaningful action ("Get told when someone's going shopping?"), never on launch. Keep push to four events: someone is going shopping, a job needs a volunteer (daily Vercel cron, which fits the Hobby plan), a thank-you for you, and an item ran out. notificationclick deep-links to /jobs/123 and similar. Because the family shares one PIN, the first run must ask "Whose phone is this?" and store the person on the device. That fixes push targeting and "who did what" in one step.
  • Install. On Android, catch beforeinstallprompt and show our own "Add to home screen" button. iOS has no prompt, so detect Safari plus !navigator.standalone and show a two-step Share → Add to Home Screen sheet. The manifest needs display: standalone, start_url: /, and 192/512 maskable icons. Opera Mini, common in Kenya, doesn't run service workers, so tell everyone to use Chrome (or Safari on iPhone) and detect it on first open.
  • Navigation (revises 02). Material 3 allows 3-5 destinations. Use Home · Shop · Jobs · Meals · More, with Money, Budget, Meeting and Contacts under More. Dad is remote and mostly uses Money, so let More remember the last section he opened. Each tab keeps its own stack, and Android back goes sub-screen → tab root → Home → exit. An iOS standalone app has no browser back button, so every sub-screen needs an in-app back arrow.
  • Data-light (revises 05). Budget about 170 KB gzipped JS for the first load and close to 0 KB on later opens. Use system fonts and SVG icons, with no web fonts or images. GSAP core (~25 KB) for small transitions is fine. Leave Lenis's syncTouch off so phones keep native momentum scroll and pull-to-refresh; on touch it then costs ~4 KB and does nothing. Keep React Bits off the daily screens; one on an empty state at most. Respect prefers-reduced-motion.
  • Plan revisions. Drop "Claude accounts". Tap-to-call now works (tel:), so the caveat in 02 §8 goes. "Summary for Dad" should use navigator.share straight into WhatsApp, with copy as the fallback. Receipt photos (later) can use <input type="file" accept="image/*" capture> with no permission plumbing, but compress to under 200 KB first.

Test matrix: (1) a low-end Android Go-class phone, Chrome, battery saver on; (2) a mid-range Samsung; (3) the family iPhone, after checking it runs iOS 16.4+ (iPhone 7 and older can't get push). Scenarios: airplane mode → edit → reconnect; two phones both drop beans offline → both deltas land; swipe the app away mid-save; force-stop Chrome, then send a push; Tecno/Infinix battery manager killing Chrome; clear site data with unsynced rows; Chrome DevTools Slow 3G + 4x CPU throttle on every PR.

Risks if ignored:

  • Server-rendered pages or SW-cached API responses give blank screens or stale balances offline, and the family loses trust in the money numbers.
  • Push "silently" fails: the iPhone isn't installed or is below 16.4, or HiOS/XOS/MIUI battery managers delay delivery (setup step: set Chrome battery to "Unrestricted"). The "I'm going shopping" coordination then breaks.
  • Lost writes: absolute-value stock sync overwrites a sibling's change, or unsynced outbox rows vanish with no warning on eviction or a reinstall.

Overview

A family-owned, installable web app (PWA) built with Next.js on Vercel and Supabase, under the owner's existing free-tier accounts. Six members (Mom, sister, two brothers, the owner, and Dad remotely) open it from one link, add it to the home screen, unlock with a family PIN and pick their name once per phone. Every section reads offline and every action except claiming a job or cooking slot can be done offline, syncing on reconnect.

All 8 sections ship in release 1 and launch at family meeting 1. Stock & Shopping, Jobs and Money are built first and deepest. Home, Meeting, Meals and Contacts are plain but correct. Three push notifications at launch. The app never ranks people: no per-person totals, thank-yous go only to the person thanked, and "Needs a volunteer" names the job, not people.

Architecture

  • Stack: Next.js (App Router) PWA, every data page client-rendered; Serwist service worker precaches the app shell; Dexie (IndexedDB) holds a local copy of all tables; Supabase Postgres with RLS, one Edge Function (notify), pg_cron, pg_net.
  • Sign-in: each phone signs in to Supabase anonymously. /api/unlock checks the family PIN against a bcrypt hash on the server, rate-limited per IP (5 per 15 min) plus a global cap (30 per hour, then 1-hour lock and an alert to the owner). Then "Who are you?" links the device to a member. is_household() checks the devices row (revoked_at is null, member_id set) on every request. Lost phone: revoke that device. Leaked PIN: change PIN, which revokes all devices. First unlock needs signal; afterwards the saved session opens offline.
  • Attribution: actor_id is filled by the database from the device's member, overwriting anything the phone sends.
  • Sync: outbox in Dexie, flushed on open, reconnect, focus and every 30 s while visible (Background Sync tag on Android). One apply_mutations RPC, SECURITY INVOKER, hard table/column allowlist, idempotent on mutation id, returns a reason for each rejection. Pull by updated_at cursor; soft deletes (deleted_at) everywhere. Realtime nudges a pull while open.
  • Conflict rules: stock as +/- movements (sum is the count); money insert-only, corrections via voids_entry_id; claims server-checked, first claim wins, online only; everything else last-write-wins per row.
  • Data: 25 tables and 3 views (shopping_needed, money_balance, budget_vs_actual). See deliberation/round3/architect.md.
  • Push: trigger on activity calls notify via pg_net with a shared-secret header. notify applies quiet hours 21:00-07:00 Nairobi, per-person on/off, global kill switch, 60-second per-person grouping, drops events older than 1 hour, deletes dead subscriptions, logs failures.
  • Scheduled: pg_cron daily flags jobs unclaimed for N days (default 3) and recreates repeating jobs. Nightly GitHub Action: pg_dump, age-encrypted, plus one REST call so the free project doesn't pause.
  • Repo: app/(tabs)/{home,shop,jobs,money}, app/more/{meals,meeting,contacts}, app/unlock, app/who, app/api/{unlock,revoke}, lib/sync, lib/supabase, supabase/{migrations,seed.sql,functions/notify}, scripts/setup-env.mjs, .env.example, .github/workflows/backup.yml.

User Experience

  • Bottom bar: Home · Shop · Jobs · Money · More. More holds Meals, Meeting, Contacts, Settings and remembers the last one opened. Budget is a tab inside Money.
  • Home ("Today"): greeting, contact search, at most 5 cards by urgency: items Out, "X is heading to [shop]", open help requests, Today's meals with "I'll cook", Money left.
  • 5-second rule: taps save on the phone first, show "Saved on this phone · will sync", and offer Undo instead of confirm dialogs. Produce uses one-tap OK/Low/Out; packaged goods use +/-.
  • Volunteer mechanics: Open / Taken / Done; dropping a job asks no reason and sends no alert; "Waiting 3 days · on the next meeting agenda"; one-tap "Asante" thank-you, push to recipient only. Money-in entries can be thanked too.
  • Language: English with the family's own words (unga, sukuma wiki, mama mboga, fundi, KPLC tokens, Asante). KES 1,250. Tue 21 Oct. Nairobi time.
  • Offline and errors: offline banner, "N changes not synced" badge, rejected changes listed with a plain reason ("Brian already took this job. Your change wasn't saved."). Claims offline are greyed: "Taking a job needs signal, so two people don't pick the same one."
  • Onboarding (meeting 1): data pre-loaded, Mom walked through privately first, install to home screen, PIN, pick name, explain the 3 notifications, then Allow; first action is an Asante during the appreciation round; each person taps one low item and watches it sync; log Dad's latest transfer together. Dad gets the link on WhatsApp, PIN sent separately.

Visual Design and Motion

  • Identity: warm Nairobi home. Jacaranda purple brand, warm paper (light) / charcoal (dark), chai as decoration, a CSS kanga stripe on the header and thank-you cards only. Status is icon + word + colour (OK green, Low amber, Out red), never the brand colour.
  • Type: self-hosted Atkinson Hyperlegible Next 400/700 (UI) and Young Serif (titles, thank-yous), 55 KB or less; tabular figures for KES. 48px minimum targets, 56px for stock +/-.
  • Motion (owner's GSAP + Lenis + React Bits stack, sized for budget phones): GSAP for 9 feedback moments (stock tap, shopping tick, put away, claim confirmed, done + thank-you, tab/sheet, money-left tween, sync banner); React Bits SplitText only, for the daily greeting; Lenis only on money history and the meeting archive with touch smoothing off. Transforms and opacity only, every moment has a reduced-motion fallback, no WebGL, no scroll-linked effects. Tokens and motion table in deliberation/round3/artisan.md.
  • Budget: first load at most ~250 KB; later opens near zero.

Quality Strategy

  • Every build phase ends with a two-phone check (see Build Plan).
  • 11-scenario device matrix on a low-end Android, a mid-range Samsung and the family iPhone (deliberation/round3/pathfinder.md): offline edits, offline deltas on two phones, claim race, app killed mid-save, push with app closed, quiet hours, cleared storage, Slow 3G cold start, reduced motion + dark, revoked device.
  • Automated: database tests for RLS and money insert-only, unit tests for the sync outbox and conflict rules, Playwright for the main journeys.
